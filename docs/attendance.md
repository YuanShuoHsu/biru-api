# 員工出勤與薪資

介面只放在 biru-admin；biru 同步共用 API 型別。biru-admin 沒有 `/attendance` 頁面，入口是 `/[locale]/attendance/mine?organization=<slug>`。側邊選單的「員工出勤」只負責展開子項。各分頁使用 `/attendance/<tab>` 子路由與共用的 `AttendanceTabsLayout`；管理分頁依各自資源的權限顯示，沒有權限時回 404。使用既有組織會員、MUI、SWR、React Hook Form、Zod 與五語系翻譯。

## 權限與操作

| 角色   | 可用功能                                                   |
| ------ | ---------------------------------------------------------- |
| member | 自己的打卡、補卡、請假、加班申請、休假額度及已發布薪資單   |
| admin  | member 功能，加上員工啟用、排班、額度核給與申請審核        |
| owner  | admin 功能，加上出勤／假別設定、薪資條件、試算、覆核及發布 |

權限以資源加 CRUD 動詞授予：`employee`、`shift`、`attendanceRequest`、`leaveCase`、`leaveBalance`、`parentalChild`、`parentalReturn` 屬 admin 與 owner；`attendanceSetting`、`leaveType`、`payrollTerm`、`payslip` 只屬 owner。自助端點（`/me/*`、打卡、送出與撤回申請、假別清單）不需要上述任何權限，只要求組織成員身分，資料範圍由服務依登入者過濾；能否打卡取決於主管是否啟用該員工的出勤資格。

申請人不能審核自己的補卡、請假、加班或撤假，須由另一位主管處理。薪資 API 由 owner 權限保護，員工只能讀取自己的已發布版本。

先在組織成員管理加入員工，再由主管啟用出勤資格並設定到職日期。班表不可重疊。複製週排班時，逐班無法排入的（假日、休息日、例假、已有班、請假等）跳過並列出原因，只複製平日班；七休一、連續上班、班距等整週法規檢查不通過則整批不寫入。班次可跨夜、同一天可有多班。班次可指定休息時段，休息須落在班次內；未計薪的排定休息不算工作時間，請假分鐘數、請假扣薪、醫療假日數換算、時薪假日排定工時與缺勤／加班檢查都會扣除，未指定休息的班次則整段視為工作時間。已有打卡或相關申請的班次不能直接取消。

上下班及休息事件使用伺服器時間。補卡須提供完整時序，核准後作為有效紀錄，原始事件仍保留。休息預設依班次是否計薪，補卡明細可指定每段休息是否計薪。核准請假會扣除額度；已核准假單必須經撤假審核才返還額度。

班表、申請與薪資單列表共用後台既有的 DataGrid 管線：快速搜尋、單一欄位篩選與排序都在後端執行，條件記在 URL。出勤 CSV 依目前篩選條件讀取所有分頁；大量資料匯出期間若有人異動紀錄，可能影響分頁結果，匯出不是資料庫快照。薪資單可列印及匯出 CSV。

## 啟用

1. 在 biru-api 依現有部署流程，對確認的目標資料庫依序套用 `0122_attendance.sql`、`0123_payroll_and_templates.sql`、`0124_payroll_versions.sql`、`0125_statutory_leave.sql`、`0126_emergency_makeup_rest.sql`、`0127_event_leave_cases.sql`、`0128_calendar_leave_pay.sql`、`0129_payroll_rule_sets.sql`、`0130_parental_leave.sql`、`0131_parental_children_and_returns.sql`、`0132_attendance_indexes_and_parental.sql`、`0133_attendance_request_shift_idx.sql`、`0134_attendance_retention_indexes.sql`、`0135_shift_breaks_and_part_time_grades.sql`、`0136_payroll_rule_set_freshness.sql`、`0137_payroll_reopen.sql`、`0138_employee_weekly_minutes_history.sql`、`0139_attendance_organization_fk.sql`、`0140_attendance_retention_restrict.sql` 及之前尚未套用的 migration。0122–0131 已在隔離 PostgreSQL 18 驗證，0122–0136 另以 PGlite（PostgreSQL 17）驗證；0137–0140 尚未重播，未查證或套用正式資料庫。
2. 部署更新後的 biru-api 與 biru-admin；API 型別依更新模組的 Swagger 產生。班次休息時段、勞保 `laborLadder`、兩個新阻擋原因與平台管理員確認每小時最低工資的畫面，須在 biru-admin 補上。
3. 部署後由平台管理員執行一次 `POST /api/payroll/rule-sets/ingest`。規則集尚未在薪資月份開始後成功同步前（兩份分級表都要取得，且沒有任何期間因數值不合理被退回），所有薪資草稿都會被 `payrollRuleSetStale` 阻擋。
4. owner 設定店家經緯度、範圍及固定公網 IP，新增假別及薪資條件。主管啟用員工，設定到職日與每週約定工時並排班。自訂假別需人工核給額度；法定假別依以下規則計算。
5. 在實際 HTTPS 網址驗證 GPS 與網路。定位需在 60 秒內，定位誤差加上距離須在店家範圍內，且來源 IP 必須同時通過白名單。

後端使用 `app.set('trust proxy', trustedProxies())`，信任清單讀自 `TRUSTED_PROXIES`，以逗號分隔 IP、CIDR 或 proxy-addr preset。未設定時不信任任何代理，`req.ip` 會是直接連線的位址；格式錯誤時啟動失敗。清單只能列出實際轉送請求的代理，否則客戶端可偽造 X-Forwarded-For，影響打卡 IP 白名單。[Express 代理信任規則](https://expressjs.com/en/guide/behind-proxies/)

Render 終止 TLS 不保證轉送標頭已被清理，Next rewrite 也不提供這項保證。

部署驗收需涵蓋直接 API、Next rewrite、自訂網域及可用的 onrender.com 入口：正常店家來源應通過，非店家來源及偽造白名單 X-Forwarded-For 應拒絕。`TRUSTED_PROXIES` 要填哪些位址，須以實際代理鏈確認。

Wi-Fi 區網 IP 不可當成店家固定公網 IP。GPS 與 IP 是出勤條件驗證，並非裝置定位防偽機制。

## 薪資計算範圍

目前限定台灣、Asia/Taipei、一般工時、TWD、月薪／時薪與每月結算；費率、投保級距與最低工資依薪資月份套用當期規則集。班次日期類型須由主管正確指定；系統不自動判定國定假日或個別員工的休息日。薪資條件限月初生效；同一生效日修改會新增版本。

金額以分為單位儲存並使用整數運算。一般工作日、休息日與國定假日按不同規則計算；加班需對應實際核准時段。雇主退休金提繳不從員工實領薪資扣除。投保金額由 owner 輸入，須是當期官方級距中的一級；系統不自動申報，也不依薪資自動選級。

一般保費自動模式支援勞保／就保、健保眷屬上限與退休金；特殊身分、補助或其他計算方式需關閉自動模式，填入已核定金額和依據。所得稅可填已確認金額，或在員工確實選用時選擇居住者 5% 扣繳；未實作非居住者、扣繳表及申報整合。

已支援跨月班次：按實際工作區間拆分薪資月份，沿用同一工作日的加班級距；不會在月界重新累計前 8 小時。月中到離職須由 owner 選擇 30 日或當月實際日數比例；離職時間為不再受僱的起點，不包含該時間之後。自動保費模式依受僱期間推算加退保天數，與實際投保日期不同時須使用核定金額模式。

同班請假與出勤可結算，但兩者時間不能重疊。時薪固定津貼須填入核定的每月換算工時。例假緊急出勤須另由主管確認法定事由、通報時間與至少 24 小時補休區間；補休日不能再排入重疊班次。這是紀錄與薪資流程，不會代替向主管機關通報。

仍會阻止覆核及發布的情況包括未完成出勤或申請、未核准加班、缺少計薪依據、工時／最低工資檢查不符、投保金額不在當期級距（`insuranceBasisOutdated`）、規則集尚未同步確認（`payrollRuleSetStale`）、時薪人員的每小時最低工資尚待確認（`minimumWageUnconfirmed`）、已改為全時工作卻仍套用部分工時勞保級距（`partTimeLadderRequiresPartTime`）、負實領等。不可改寫出勤資料繞過限制；有工時違規的既有出勤仍涉及工資給付，須另由負責人處理，系統尚無違規案件專用結算流程。

每週工時有生效日：修改工時必須填生效日，不得早於到職日，且生效日落在已關帳月份時同樣要先重新開帳。特別休假與事假、家庭照顧假、病假的年度額度，一律依「該期間起始日」當時的工時比例計給，之後調整工時不會回頭減少已取得的假；病假天數換算依請假當日工時，事件假依案件起始日，部分工時勞保級距依薪資月份。員工資料保留完整工時異動歷程。

## 投保級距與規則集

`payroll_rule_set` 每個生效期間一筆，薪資草稿依月份選用當時有效的一筆，重算舊月份仍使用舊規則。每天凌晨 4 點（Asia/Taipei）從政府開放資料同步勞保（[data.gov.tw 6258](https://data.gov.tw/dataset/6258)）與健保（[data.gov.tw 20251](https://data.gov.tw/dataset/20251)）分級表，平台管理員也可手動執行。兩份表都成功取得才記錄確認時間；下限或上限下降、或超過兩倍的級距視為來源異常並沿用前期。

勞保分為一般勞工與部分工時勞工兩條級距，部分工時級距自 11,100 元起；薪資條件以 `laborLadder` 選擇，選部分工時時員工每週約定工時須少於 40 小時。健保沒有部分工時級距，下限仍為分級表第一級（[健保署承保問答](https://www.nhi.gov.tw/ch/dl-7767-9c7e2b52e55a4dbe9f4f5ae4cbd880bc-1.pdf)）。

費率與最低工資沒有官方 API。費率沿用前期（記錄於 `rates_carried_from`），公告調整時須另以 migration 更新。每月最低工資取一般勞工級距第一級；每小時最低工資無法推得，月最低工資變動時該期標記為待確認，時薪人員的草稿會被阻擋，直到平台管理員以 `PATCH /api/payroll/rule-sets/:effectiveFrom` 依[勞動部公告](https://www.mol.gov.tw/1607/28162/28166/28180/70460/76761/)填入金額與來源。

## 假別與事件額度

年資特休採到職週年制，滿半年、1 年及後續年資自動計算，依每週約定工時調整部分工時額度。未休特休在週年屆滿或離職月份列入薪資；未提供協議遞延流程。事假、家庭照顧假、非住院病假及生理假依年度／月份計算額度，家庭照顧假共用事假額度，生理假超過年度前 3 日部分併入病假。

婚假、三種親屬關係的喪假、產檢假、陪產檢及陪產假、產假及三種流產假採事件額度：主管在「事件假額度」確認事件編號、資格依據及有效期間後，系統計算法定額度。員工申請時選擇該事件；主管不能替自己核給事件。相同員工／假別／事件編號不可重複，撤假審核完成才釋出已用額度。事件與親屬關係、妊娠或分娩等事實仍須由主管確認。

產假／流產假含例休日，以完整曆日計算。owner 必須填入核定每日全薪（單位為分，應含法定工資範圍），系統按年資計算給薪比例。月薪底薪先扣除該期產假占用部分，再加入依核定日薪計算的產假工資；部分月份須選擇底薪比例。未排班且整個受僱期間都在產假時也可結算。產檢／陪產檢以排定工時計算，陪產檢與陪產共用同一事件的 7 日額度。日薪依據需符合[勞動部產假工資說明](https://www.mol.gov.tw/1607/28690/2282/2284/2294/7269/)。

本輪已加入住院傷病／安胎休養的本年加前一年共用額度、醫療證明核准確認、生理假半薪／超額無薪時間分段，以及育嬰留職停薪的子女事件、按日／連續申請與期間限制。醫療假半薪與無薪採實際時間分段；撤假核准後重新計算給薪額度。育嬰期間禁止打卡，撤假核准後才恢復；整月留停不需建立虛構班次，月薪與時薪固定津貼均扣除留停部分。育嬰期間須關閉自動保費，由 owner 填入核定保費、退休金與依據後重新產生草稿；不自動辦理續保、津貼申領或政府申報。年資目前保留累計，未提供不計留停年資的選項。公假、公傷病等依個案核定期間或給付的情境，目前仍使用自訂假別與人工核定流程。

育嬰案件需選擇已核定的「子女資料」，同一子女跨事件編號仍共用額度。主管以查驗證明後的固定識別編號建立資料，雙胞胎分別登錄；不可因新申請再次為同一子女建立不同識別。舊案件不依生日自動合併，須在事件假額度完成子女歸戶；仍有未歸戶案件時，系統阻擋該員工新增育嬰核准。

員工在已核准育嬰假單選擇「提前復職」，填入復職日期與原因；主管在「復職申請」審核，不能自行核准。待審期間維持原留停與打卡限制，也可撤回申請。核准後保留已休期間、原截止日及申請／審核紀錄，只釋出未休額度。待審復職只阻擋預定復職日起受影響月份的薪資結算；之前月份的指紋不因縮短未來留停而變動。若受影響月份已有發布薪資，復職變更會被阻擋。

育嬰期間即使保留假日／例假排班，時薪也不會因此產生未出勤底薪；跨月班次依留停重疊部分扣除，保留留停以外的正常假日給薪與原 8 小時計薪上限。

草稿保存來源指紋、規則版本、金額與明細。覆核／發布前重算並比對來源；資料變動後必須產生新草稿。舊版本保留，發布不會觸發匯款或政府申報。

薪資一經發布，該員工該月即關帳：核准申請或撤假、新增或取消班次、儲存薪資條件、變更到職日或離職日、提前復職及重新試算，只要影響已發布月份都會回傳 `payrollLocked`。請假核准自請假起始月起鎖定之後所有月份，因病假與特休累計會影響後續月份；變更到職日或離職日則自新舊日期較早者起鎖定。

需要更正已發布月份時，由主管在該薪資單執行「重新開帳」並填寫原因，不能對自己的薪資單執行。開帳後該月解除鎖定，可修正出勤或條件並產生新版本草稿，覆核發布後重新關帳。原版本保留 `reopenedBy`／`reopenedAt`／`reopenReason`，員工仍看得到已發布的各版本。
