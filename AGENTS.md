# AGENTS.md

This file provides guidance to coding agents (Claude Code, Codex) when working with code in this repository.

## Commands

```bash
# Development
pnpm run start:dev       # Start with hot reload
pnpm run build           # Compile TypeScript to ./dist (errors are ANSI-coloured; judge success by the exit code, not by grepping the output)
pnpm run start:prod      # Run production build

# Testing
pnpm run test            # Run unit tests
pnpm run test:watch      # Watch mode
pnpm run test:cov        # Coverage report
pnpm run test:e2e        # End-to-end tests: AppModule on in-memory PGlite (db module mocked); a local .env still fills vars the spec leaves unset

# Code Quality
pnpm run lint            # oxlint (type-aware)
pnpm run format          # Prettier format

# Database (Drizzle Kit)
pnpm drizzle-kit generate   # Generate migration from schema changes
pnpm drizzle-kit migrate    # Apply pending migrations
pnpm drizzle-kit studio     # Open Drizzle Studio GUI
```

To run a single test file:

```bash
pnpm vitest run src/payroll/payroll.service.spec.ts
```

Branch from `develop` and open every PR against `develop`. GitHub's default branch is `master`, so set the base explicitly (`gh pr create --base develop`): a PR merged only into `master` never reaches `develop`, so work branched from `develop` misses it and conflicts when `master` is merged back.

## Architecture

**Biru Coffee** is a multi-language coffee shop management API (NestJS 12, TypeScript, PostgreSQL).

### Key Stack

- **Framework**: NestJS with Drizzle ORM (PostgreSQL via `pg` driver, Supabase hosted)
- **Modules**: native ESM (`"type": "module"`); local imports are relative paths ending in `.js`
- **Auth**: `better-auth` library wrapped in `AuthModule` — handles email/password registration, verification, and Google OAuth
- **i18n**: `nestjs-i18n` supporting `en`, `ja`, `ko`, `zh-CN`, `zh-TW`; resolved by `LanguageResolver` (`src/common/resolvers/`) from the `lang` query param, then `x-lang`, then `Accept-Language`, each normalised by `pickLanguage` (`src/common/utils/language.ts`, q-ordered, `zh-HK`/`zh-Hant` → `zh-TW`) — use it rather than nestjs-i18n's built-in resolvers
  — emails and notifications use the recipient's `user.lang`, not the request: Google sign-up sets it from the page language (`src/auth/sign-up-language.ts`), and both frontends save it when a signed-in user picks a language from the language menu (visiting another locale's URL does not change it)
  — `src/generated/i18n.generated.ts` is regenerated by the running app (at boot and whenever `dist/i18n` changes), never by `build`, so after adding a key to `src/i18n/*/*.json`, run the app once before writing the `i18n.t()` call that uses it, or `build` fails on the unknown key. If the app can't boot (no database), add the key's `"<key>": string;` line by hand in alphabetical order, which is what the generator writes, and check it is unchanged the next time the app runs
  — for the same reason, stop the app (`start:dev` included) before running `build` from the same checkout: `build` deletes `dist/`, the app rewrites the file almost empty, and `build` then fails on every `i18n.t()` call. Recover with `git checkout -- src/generated/i18n.generated.ts`
- **Payments**: ECPay integration (`src/ecpay/`) with AIO checkout and invoice services
- **Real-time**: Socket.io gateway in `src/events/`
- **Email**: Nodemailer + Handlebars templates in `src/mails/`

  the attendance and payroll tables use `withTimezone: true` instead, so don't switch them to the helper.

A DTO cap on a Postgres `integer` column must leave room for the code that adds to the stored value: new rows are
appended at max `sortOrder` + 1 or prepended at 0 with every existing row shifted +1, and `reorderSortOrders`
(`src/common/utils/sort-order.ts`) renumbers upwards, so cap such fields at a domain size (e.g. `@Max(9999)`), never at
2147483647, or the overflow 500 only moves to the next insert.

Migrations are in `drizzle/` and applied with Drizzle Kit. The `drizzle.config.ts` at root reads `DATABASE_URL` from `.env`.

Every business table has a `record_deleted_row` BEFORE DELETE trigger that copies the row into `deleted_record` (cascaded children land in the same `batch_id`, i.e. the same transaction). The trigger was attached in `0190` to the tables that existed then, so **a new table needs its own `CREATE TRIGGER` in the migration that creates it**, unless it belongs in `UNTRACKED_TABLES` (`src/deleted-records/deleted-record-tables.ts`, kept in sync with the migration). The app logs a warning at startup for tables missing the trigger. Rows are purged after 30 days; batches whose root table is in `RESTORABLE_TABLES` can be restored by platform admins, or by store members whose role holds that table's `RESTORE_PERMISSIONS` action (restoring an owner member or invitation needs `owner`). Scheduled retention purges must run `set_config('app.skip_deleted_record', 'on', true)` inside their transaction so expiry isn't captured as a deletion (see `TasksService.purge`); never use a session-level `SET` on the pool.

### Payroll Rule Sets

Insurance rates, 投保級距 and 最低工資 are **not** constants in code. `payroll_rule_set` holds one row per
effective period (`effective_from`, `YYYY-MM`) with the rates, the 級距 ladders, the source URLs,
and `rates_carried_from`. `PayrollService.snapshot` resolves the row in force for the statement's
month, so re-drafting an old month always uses that month's rates; a month with no row at all
raises `payrollRuleSetMissing`.

`PayrollRulesService.ingest()` refreshes the rule sets from six of the official open-data datasets listed in
`src/payroll/rule-source.ts` — 勞保分級表 (`6258`), 職災保險投保薪資分級表 (`170557`), 勞退月提繳分級表 (`6274`),
健保投保金額分級表 (`20251`), 最低工資 (`6281`) and 職災保險費率 (`6262`) — each discovered through
`data.gov.tw/api/v2/rest/dataset/{id}` so new years need no code change. 職災 industry and
commuting rates come from `6262`; the other rates
are carried forward from the previous period rather than guessed, because they are statutory
(勞保 11.5% + 就保 1%, 健保 5.17%, 薪資 5% 就源扣繳) and change only by announcement. An ingested ladder
whose floor or ceiling moves down, or more than doubles, is rejected as a source change and the
previous ladder is kept. The withholding floor is `各類所得扣繳率標準` §13 — 應扣繳稅額 not over NT$2,000 — **not** a salary
threshold. Seeded for 2026-01 in `drizzle/0129_payroll_rule_sets.sql`; refreshed daily by
`TasksService` and on demand via `POST /api/payroll/rule-sets/ingest` (platform admin).
The same job and endpoint also run `ingestHolidays`, which rewrites `statutory_holiday` for the current and later
years from 政府行政機關辦公日曆表 (`14718`) and returns the years written as `holidayYears`. Of the past years only the
previous one is backfilled: written once while it has no rows, never rewritten; older years are never fetched. `0164`
seeds no holidays, so until a year is written, scheduling and drafts in it fail with `holidayCalendarMissing`.
Each year is rewritten under a per-year advisory lock, so the cron and a manual run never interleave.

最低工資 comes from dataset `6281`. When it has no usable figure for the period — unreachable, rejected for
showing a decrease, or below the 一般勞工 ladder's first grade (which the 分級表 ties to the monthly 最低工資) —
the monthly figure is taken from that first grade and the hourly one is carried from the previous period. If
that changes the monthly figure, the period gets `unconfirmed: ['minimumHourlyWageCents']` and hourly drafts
carry `minimumWageUnconfirmed` until a later ingest finds the figure in `6281` or a platform admin sets the
announced value via `PATCH /api/payroll/rule-sets/:effectiveFrom`.

An ingest that fetched every dataset and rejected nothing stamps `checked_at` on the latest period. A draft whose rule set is
the latest and was not checked on or after the start of the payroll month carries
`payrollRuleSetStale` — a failed January fetch must not silently bill last year's ladder. After deploying
`checked_at`, run one ingest or every draft is held.

勞保 has two ladders: `laborGrades` (一般勞工) and `partTimeLaborGrades` (部分工時勞工, floor NT$11,100),
chosen by `insurance.laborLadder`, which saving terms derives (`deriveInsurance`): `partTime` unless the employee
is known full-time at the terms' `effectiveFrom` (see Weekly Hours). A draft whose terms carry `partTime` for an
employee known full-time at the period start carries `partTimeLadderRequiresPartTime`.
健保 has no part-time ladder — its floor stays 分級表第一級.

If an employee's stored `laborBasis` / `healthBasis` is not a grade in that month's ladder — what
happens every January when 最低工資 moves the floor — the draft carries an
`insuranceBasisOutdated` blocker instead of billing the stale grade.

### Published Payslips

A month with a `published` statement is closed for that employee. Anything that changes what its snapshot
reads — approving a request or a leave cancellation, creating or cancelling a shift, saving terms,
parental returns, moving `hiredAt` / `terminatedAt`, re-drafting the month — must call
`assertPayrollUnlocked` (`src/attendance/attendance-audit.ts`) first and fails with `payrollLocked`.
Leave approvals lock every month from the leave start onward, because medical and annual leave ledgers
carry into later months. Creating, updating, cancelling or restoring a workday shift — and an indigenous holiday
change or 國定假日補休 that flips a shift between workday and holiday — likewise lock every month from the shift
start onward (an update checks the old and new shift, each by its own day kind), because weekly hours are a rolling average
of workday shifts and leave quotas read them at the period start. Other shifts lock only their own months.

There is no reopen: `payroll_statement` holds one statement per employee and month
(`payroll_statement_month_uidx`, migration `0157`), so a published month stays closed.

### Attendance Audit

Attendance and payroll changes are audited by `writeAudit` (`src/attendance/attendance-audit.ts`) into
`attendance_audit`, **not** by `@Audit` / `audit_log`. The row is written inside the same transaction as the
change, and it is kept 60 months — 勞基法 §30 requires attendance records for five years, while `audit_log`
is purged after 12. Don't add `@Audit` to attendance or payroll handlers, and don't move these rows into
`audit_log`.

Both tables are shown together on the 異動紀錄 page: `AuditService` unions them, mapping each
`attendance_audit.action` through `ATTENDANCE_AUDIT_ACTIONS` to a resource and verb. A new attendance action
must be added there (the `writeAudit` signature enforces it), and a new resource needs an entry in
`READ_PERMISSIONS` (`src/audit/attendance-audit-entries.ts`) so members without that data's read permission
never see its history.

The attendance and payroll record tables (employees, shifts, events, requests, leave cases and balances,
parental records, payroll terms, statements, earnings, tax identities, certificate requests) reference
`organization` with `ON DELETE restrict` (like `order`), so an organization holding them cannot be deleted;
don't switch them back to cascade. The per-store settings and lookup tables — `attendance_settings`,
`attendance_shift_type`, `attendance_leave_type`, `payroll_earning_type`, `payroll_withholding_unit` — and
`attendance_audit` cascade with the organization: the deletion can only happen once no
restricted record is left, and the cascaded rows are captured in `deleted_record` like any other deletion.

### Weekly Hours

An employee's weekly hours are not stored (`0144` dropped `weekly_minutes` and `weekly_minutes_history`); they
are derived from the schedule. `averageWeeklyMinutes` (`src/attendance/employee-hours.ts`) averages the
employee's non-cancelled `workday` shifts that ended in the 12 months before the date — from `hiredAt` or the
first such shift if later — counting each shift's `scheduledWorkSeconds` capped at 480 minutes, and is `null`
when no such shift ended in that window. `weeklyMinutesAt` / `weeklyMinutesOf` fall back to
`FULL_TIME_WEEKLY_MINUTES` (2400) for `null`; `averageWeeklyMinutesSql` / `employmentTypeSql` are the SQL form
for lists and average up to `now()`. Under 2400 is part-time.

Resolve the hours for the date that governs the entitlement. 特別休假 and the yearly 事假 / 家庭照顧假 / 病假
quotas are granted at the period start (勞基法 §38: the right vests when the period is reached), so
`annualLeavePeriod` and `statutoryLeavePeriod` resolve the hours at `period.start` and shifts after it cannot
shrink leave already granted. Medical-leave day conversion and quotas resolve at the start of the calendar year
(住院 at the previous year's start), event leave at the case start. The 勞保 part-time ladder instead uses
`knownFullTime` (`src/payroll/payroll.service.ts`), which reads `averageWeeklyMinutes` without the fallback, so
an employee with no shift history is not known full-time. Because the rolling average feeds later months, workday
shift changes lock every month from the shift start onward (see Published Payslips).

### Scheduled Breaks

`attendance_shift.breaks` (a jsonb list since `0155`; shift templates were dropped in `0176`) holds the scheduled
breaks, which `scheduledBreaks` (`src/attendance/shift-intervals.ts`) generates when a shift is saved — one
30-minute break for every 4 hours of continuous work, spread evenly, none for a shift of 4 hours or less
(勞基法 §35, [law.moj.gov.tw](https://law.moj.gov.tw/LawClass/LawSingle.aspx?pcode=N0030001&flno=35)) — so
they are never entered by hand. Unless `paidBreak` (shifts are saved with it off), they are not working time:
leave minutes, leave pay deductions, medical leave units and the hourly scheduled hours all go through
`scheduledWorkIntervals`, never the raw shift span. A shift without a break keeps its whole span as working time.

### Localized Fields

Menu entities (menus, sections, items, modifiers) store localized copy as `jsonb` typed with
`LocalizedText` — `Partial<Record<Language, string>>`, i.e. `{ en, ja, ko, "zh-CN", "zh-TW" }`,
defined in `src/db/schema/enums.ts`. Input DTOs type them as `LocalizedText` with `@IsLocalizedText()`
(`src/common/decorators/`, which only accepts the five language keys with string values; see
`src/menus/dto/create-menu.dto.ts`), and every DTO documents them with `type: LocalizedTextDto`
(`src/common/dto/`) so codegen does not emit `Record<string, never>`.

### Images

Menu, section, item, banner and store photo images are stored as base64 data URLs, unless R2 is configured (see
Environment Variables): then `ImageStorageService` (`src/images/image-storage.service.ts`) uploads each new image before
the write, keyed `<kind>/<imageVersion>.<ext>`, and the column stores its public `https://` URL, which every helper below
returns as `imageUrl` unchanged. For data URLs, their endpoints return `imageUrl` from `withImageUrl`
(`src/images/image-url.ts`), `/api/images/:kind/:id/:version.:ext` (`imageVersion`:
the first 16 hex digits of the data URL's SHA-256; a query that only needs the URL selects `imageRefSql` instead of the
image (`imageRefQuery`) and passes it to `withImageRefUrl`, as the order menu and the menu, banner and store photo
lists do, so the image never leaves Postgres; a paginated list selects the page `withoutImage` and adds `withImageRefs`
afterwards, because in the paged query Postgres would hash every matching row, not just the page), which
`ImagesController` serves with no throttling and, for the current version, a one-year `immutable` cache (`audit_log.changes` still keeps the data
URLs). Edit dialogs send `image` only when the upload differs from `imageUrl`, never the URL itself. Only a new image
moves the URL — reordering, toggling or editing other fields keeps it, so browsers and the image optimizer keep their
copy; a stale
version or extension still serves the current image (fetched from its R2 URL once the row has moved there), with `no-cache` instead of `immutable`, because the storefront
caches the banner and store photo lists (`"use cache"`) for longer than an edit takes, and every environment shares one
database, so no cache can be invalidated on every edit. Don't answer it with a redirect: Next's image optimizer rejects
a non-2xx response for a local image. The optimizer still keeps what it fetched from a stale URL for
`images.minimumCacheTTL` (4 hours by default), whatever `no-cache` says. Only a missing row or image answers 404. The endpoint is anonymous and does not
check whether the row is published: the URL is only handed out by endpoints that already authorize the caller, and
Next's image optimizer fetches the source without the viewer's cookies. The version is not an access check: anyone
who once had a URL keeps seeing the row's current image until the row or its image is deleted.

### Points Expiry

Points expire one year after they are earned — the end of the Taiwan day one calendar year after the
order's `paymentDate` (or the adjustment time), 2/29 falling back to 2/28 — computed by `toExpiresAt` in
`src/points/points.service.ts`. The term is fixed by design, not a setting: a configurable term gave one
member lots with different terms and was hard to explain, so don't reintroduce a validity-years field.
`expiresAt` is stamped when the lot is recorded and must not be shortened afterwards; an earned lot with
`null` was recorded before the rule existed and never expires.

### Ingredient Stock

`ingredient.inventory_level` goes negative only by overselling: an order that is already paid (OrderProblem →
OrderProcessing, `consumesInventory` in `src/orders/order-transitions.ts`) consumes without `enforceStock`, because a paid
order can't be refused, and `record` flags the ingredient `oversold` in the low-stock notification. Everything else keeps
stock non-negative: placing an order uses `enforceStock`, and counts and opening stock are validated as non-negative in
the DTOs. A negative level means the books are wrong and staff must recount; don't turn it into a reason to reject paid
orders, and don't accept negative counts.

### Email Opt-in

`user.emailSubscribed` is the member's email opt-in: the sign-up checkbox, which members change in the
storefront profile settings. No mail checks it yet; whether a mail type honours it is decided per type.
Account notices about the member's own account, such as the points expiry reminder, don't honour it.
A mail type that honours it must skip members with `emailSubscribed = false` and link to the profile
settings page so the member can opt out (個資法 §20,
[law.moj.gov.tw](https://law.moj.gov.tw/LawClass/LawSingle.aspx?pcode=I0050021&flno=20)), and goes
through one `MailsService` path that applies both, never a check at each caller.

### Roles & Auth

The `better-auth` instance is configured in `src/auth/index.ts` (admin, organization, and
multiSession plugins) and mounted at `/api/auth/*`. There are **two separate authorization
layers** — don't confuse them:

**1. Platform admin** — `user.role` (plain `text` column on `user`, set to `'user'` on signup).
Guarded by `AdminGuard` (`src/common/guards/admin.guard.ts`), which only passes for
`role === 'admin'`. Used for cross-tenant endpoints: `UsersController`, `AdminBannersController`,
`AdminCouponsController`, `AdminPayrollRulesController`, `AdminPointSettingsController`,
ECPay invoice management.

**2. Organization membership** — `member.role`, a pgEnum of `owner | admin | member`
(`src/db/schema/organizations.ts`). This is the main tenant-scoped mechanism:

- `src/auth/permissions.ts` declares one access-control statement per resource (e.g. `menu`,
  `order`, `coupon`, `revenue`, `payslip`), each listing only the actions it supports, and
  builds `owner` / `admin` / `member` roles via better-auth's `createAccessControl`.
  `isAuthorized(role, action)` is the single entry point.
- `@Roles(action, organizationParam)` (`src/menus/decorators/roles.decorator.ts`) annotates a
  handler, e.g. `@Roles({ order: ['update'] }, 'organizationSlug')`.
- `RolesGuard` (`src/menus/guards/roles.guard.ts`) is registered **globally** as `APP_GUARD` in
  `AppModule`. It resolves the session, derives the `organizationId` from whichever route param
  the decorator named — `organizationId`, `organizationSlug`, or by walking up the menu tree from
  `menuId` / `sectionId` / `menuItemId` / `offerId` / `addOnId` / `groupId` / `modifierId` —
  looks up the caller's `member` row, and calls `isAuthorized`. It also stashes the resolved
  `organizationId` on the request. Handlers **without** `@Roles` are passed through untouched.
- `@OrganizationMember(organizationParam)` (same file) runs the same guard without an action: any
  `member` of the organization (or a platform admin) passes. Use it for self-service routes (punching, own requests, own
  payslips) and scope the data to the caller's own employee row in the service.

When adding a tenant-scoped route whose param isn't already covered, extend both the
`OrganizationParam` union and the `resolveOrganizationId` switch.

**Role hierarchy** — every role holds all features and notifications of the roles below it:
platform admin ⊇ `owner` ⊇ `admin` ⊇ `member`. A platform admin counts as `owner` in every
organization, whatever their own `member` row says. When a feature or notification is limited to a role, also
give it to every role above, and never grant a lower role something a higher one lacks.
`permissions.ts` already keeps `owner` a superset of `admin` and `admin` of `member`;
`RolesGuard` and `findOrganizationRoles` (which the events gateway uses for its store-room joins and pushes) apply the
platform-admin step, the notification recipients don't yet.
A platform admin who joins a store gets `owner` with `member.joined_as_platform_admin` set; every
store must keep an owner without that flag, which `assertKeepsOwner` (`src/auth/owner-guards.ts`)
enforces on member removal, demotion and leave.

Controllers often carry a class-level `@AllowAnonymous()` (from `@thallesp/nestjs-better-auth`)
while individual handlers add `@Roles(...)` or `@UseGuards(AdminGuard)` — the guards run
independently of `@AllowAnonymous`, so this combination is intentional, not a hole.

- API prefix: `/api`
- Swagger UI at `/api`, document at `/api-json` — mounted only when `NODE_ENV !== 'production'` (`src/main.ts`), so codegen
  and `/api-json` comparisons run against a local or non-production API
  — `nest-cli.json` enables the [`@nestjs/swagger` CLI plugin](https://docs.nestjs.com/openapi/cli-plugin) with its
  defaults, so every property declared in a `*.dto.ts` / `*.entity.ts` file is documented without `@ApiProperty`:
  type and `required` come from the TypeScript declaration (`?`, not `@IsOptional()`), class-validator decorators add
  constraints such as `@Min` / `@IsIn`, and values given in `@ApiProperty*` take precedence over what the plugin infers. To
  tell whether a change alters the document (and so the frontends' `types/api.ts`), compare `/api-json` before and after
- Port: `PORT` env var (default 3001)
- `bodyParser: false` at the Nest factory — better-auth's module owns body parsing
- Global pipes: `I18nValidationPipe` with `transform`, `whitelist`, `forbidNonWhitelisted`
- Global filters: `AllExceptionsFilter` (i18n-aware, HTTP only — `useGlobalFilters` does not reach WebSocket gateways).
  A gateway binds `AllWsExceptionsFilter` (`src/common/filters/`) with class-level `@UseFilters`: any exception in a
  `@SubscribeMessage` handler (guard, pipe or the handler itself) is emitted as an `exception` event
  `{ status: 'error', message, statusCode?, ...response fields such as code, cause: { pattern, data } }` (no HTTP
  `path` / `success` / `timestamp`; a `WsException` or `HttpException` built from an object is spread as is, so `message`
  is only there if that object has one), translated like `AllExceptionsFilter` except that validation errors become
  `common.exceptions.badRequest`, `accessToken` stripped from `cause.data`; the ack is never called. Throw a translated
  `HttpException` / `WsException` to reject a message, never return `false`
  — both filters answer text Postgres refuses to store (a NUL byte: pg `22021` / `22P05`, `isUnstorableText`) with
  400 `badRequest`, so values bound for Postgres need no NUL check of their own; text sent elsewhere (ECPay, mail)
  still does
- Global guards (`AppModule`): `RolesGuard`, then `ThrottlerGuard`
- Rate limiting: 100 req / 60s globally (`THROTTLERS` in `src/common/constants/throttle.ts`). `throttleTracker` buckets
  signed-in requests by user id and the rest by `clientIp`; requests without a usable IP share one `ip:missing`
  bucket. It looks the session up itself because `AppModule`'s guards run before better-auth's `AuthGuard`, so
  `req.user` is not set yet. The anonymous order, ECPay checkout, carrier barcode check, waitlist ticket, coupon check and
  company lookup routes add 30 / min and 150 / hour with `@Throttle` on the named `anonymous` / `hourly` throttlers. Every throttler,
  the global one included, only takes effect once `CLIENT_IP_HEADER` or `TRUSTED_PROXIES` is set — without either
  `req.ip` is the proxy's address, so every caller would share one bucket and any limit would throttle the whole
  platform. The named throttlers are unlimited unless a route overrides
  them, and their `skipIf` also drops the route's override. The expected-points route is deliberately not on the named
  throttlers: it treats an inapplicable coupon as no discount instead of rejecting it, so it can't be used to guess codes
- `trust proxy` — set from `TRUSTED_PROXIES` (`src/common/trusted-proxy.ts`), a comma-separated
  list of proxy addresses/CIDRs or proxy-addr presets. **Never `true` or a hop count.** `true`
  makes `req.ip` the leftmost `X-Forwarded-For` entry, i.e. whatever the caller claims, so any
  ingress that appends rather than overwrites lets an attacker forge the shop IP and defeat the
  attendance allowlist; a hop count breaks whenever the chain length differs between the public
  API and the Next.js rewrite. Trusting by address is chain-length independent and makes a forged
  entry become `req.ip` itself, which the allowlist then rejects. Unset means `false` — `req.ip`
  is the socket peer, so the allowlist fails closed and every throttler (and better-auth's default limit) is skipped until the real
  proxy range is configured and verified with forged headers against the public API, Next.js
  rewrite, custom-domain and onrender.com paths.
  Reference: [Express behind proxies](https://expressjs.com/en/guide/behind-proxies/).
- Client IP — `clientIp` (`src/common/trusted-proxy.ts`) is what the throttler and the punch allowlist read. With
  `CLIENT_IP_HEADER` set it returns that header only when it holds a single IP, otherwise nothing (never `req.ip` or
  `X-Forwarded-For`), so the punch is rejected; unset, it returns `req.ip`. Set it only when every request reaches the
  API through Cloudflare (`CF-Connecting-IP`): any path that bypasses Cloudflare, the onrender.com subdomain included,
  lets the caller forge the header, so that subdomain must be disabled or unreachable first. Browser calls that go
  through a Next `/api/*` rewrite arrive with Vercel's egress IP, so set it only after the frontends call the API
  directly (#209). Server-side calls from the Next apps also arrive with the Next server's egress IP (or, calling
  onrender.com directly, without the header, i.e. `ip:missing`); to keep per-visitor buckets the storefront's
  server-side calls send the visitor's IP in `x-forwarded-client-ip` with `CLIENT_IP_FORWARD_SECRET` in
  `x-client-ip-forward-secret`. `forwardedClientIp` returns that IP only when the secret matches and the value is a
  single IP; the throttler tracker and better-auth (its limiter and session IP) read it, never the punch allowlist, so
  the secret can't vouch for a shop IP. The throttlers skip WebSocket messages. better-auth's own limiter
  (`/api/auth/*`, which Nest guards never see) uses the same `rateLimitClientIp`: the `BetterAuthModule` middleware
  removes any `x-biru-client-ip` the caller sent and, once `rateLimitEnabled()`, sets it to that IP;
  `advanced.ipAddress.ipAddressHeaders` reads only that header. While `rateLimitEnabled()` is false the header is never
  set, so sessions store no IP, and a `customRules` catch-all drops every limit except the stricter built-in ones
  (sign-in, sign-up, password and verification mails), which then share one bucket per path platform-wide — set
  `CLIENT_IP_HEADER` to give them per-client buckets.
- Also applied: `helmet`, `cookieParser`, CORS restricted to
  `NEXT_URL` + `NEXT_ADMIN_URL` with credentials
- `I18nMiddleware` is mounted on every route by `I18nModule.configure()`; don't add
  `app.use(I18nMiddleware)` here — Express receives the class, treats it as an error handler
  (constructor arity > 3) and never runs it on normal requests

### Environment Variables

There is no `.env.example` and `ConfigModule.forRoot` runs without a `validationSchema`, so a
missing variable fails at request time rather than at boot. Required in `.env`:

- `DATABASE_URL` — PostgreSQL connection string (read directly via `process.env` in `src/db/index.ts`)
- `BETTER_AUTH_SECRET` / `BETTER_AUTH_URL` — read implicitly by better-auth
- `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` — Google OAuth
- `MAIL_HOST` / `MAIL_USER` / `MAIL_PASS` — SMTP; `MAIL_PREVIEW=true` switches to jsonTransport + local preview
- `ECPAY_BASE_MERCHANT_ID` / `ECPAY_BASE_HASH_KEY` / `ECPAY_BASE_HASH_IV` / `ECPAY_BASE_RETURN_URL` — AIO checkout
- `ECPAY_INVOICE_MERCHANT_ID` / `ECPAY_INVOICE_HASH_KEY` / `ECPAY_INVOICE_HASH_IV` — invoicing
- `ECPAY_OPERATION_MODE` — ECPay stage vs. production endpoint selection. Also gates every
  `@Cron`: local, stage and production share one database, so cron jobs run only when this is
  `Production` (every `@Cron` must pass `disabled: !CRON_ENABLED`). `@Interval` jobs that are
  already environment-scoped are not gated
- `NEXT_URL` — Frontend origin (CORS + ECPay redirect allowlist)
- `NEXT_ADMIN_URL` — Admin frontend origin (same two uses)
- `FALLBACK_LANGUAGE` — Default i18n locale (e.g. `zh-TW`); read with `getOrThrow`
- `TRUSTED_PROXIES` — Comma-separated proxy addresses/CIDRs or proxy-addr presets. Unset means
  `trust proxy: false`, which fails the attendance IP allowlist closed; with `CLIENT_IP_HEADER` also unset, every Nest
  throttler is off and better-auth keeps only its stricter built-in limits, shared platform-wide (logged at boot when
  `NODE_ENV=production`)
- `CLIENT_IP_HEADER` — Header holding the client IP, e.g. `CF-Connecting-IP`; takes precedence over `req.ip`. Only set
  it when every request reaches the API through Cloudflare (onrender.com disabled), otherwise the header can be forged
- `CLIENT_IP_FORWARD_SECRET` — Shared with the biru storefront's server (same name there, never `NEXT_PUBLIC_`); a
  random value of at least 32 bytes. Unset means forwarded client IPs are ignored
- `FIELD_ENCRYPTION_KEYS` — `v3:<base64 32 bytes>,v2:<...>,legacy` keys for `src/common/utils/field-encryption.ts`;
  the first encrypts, the rest only decrypt. `legacy` (no key) is the key derived from `BETTER_AUTH_SECRET`,
  which writes the unprefixed `iv.tag.ciphertext` format; it is unrelated to the `-v1` in the purpose info
  strings. Unset behaves as `legacy` alone (logged at boot); a malformed value stops the app at boot.
  Local, stage and production share one database, so a key may be first only once every environment can
  decrypt it: (1) set `legacy,v2:…` everywhere; (2) once all are deployed, switch to `v2:…,legacy`. Rotate
  the same way — add the new key second everywhere, then move it first. Once prefixed ciphertext exists,
  never roll back to a build without this support. Unprefixed ciphertext keeps needing `BETTER_AUTH_SECRET`
  until it is re-encrypted; a later PR provides that script
- `R2_ACCOUNT_ID` / `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` / `R2_BUCKET` — Cloudflare R2 bucket for menu, banner and
  store photo images; all five R2 variables must be set, or new images stay base64 data URLs in Postgres
- `R2_PUBLIC_URL` — Public origin of that bucket (e.g. its custom domain); the uploaded image URL is this plus the key
- `PORT` — HTTP port (default 3001)

`JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `JWT_ACCESS_EXPIRES_IN`, `JWT_REFRESH_EXPIRES_IN`,
and `POSTMAN_API_KEY` are present in `.env` but referenced nowhere in `src/` — leftovers from
before better-auth.

## Code Comments

**Default: no comment.** Never add one just to explain; new code ships with zero comments unless asked. Write one only when its absence would cause a mistake — it states a consequence or precondition that lives outside the code:

- `// 店家角色不該取得全平台組織清單` (security reason the conditional can't show)
- `// drizzle 會把 pg 錯誤包成 DrizzleQueryError，原始錯誤碼在 cause` (framework trap)

The test: delete it. Would a competent editor now make a wrong change? If the honest answer is only "會比較難懂", leave it deleted.

**Exception: official documentation links are wanted.** When code follows a specific page of the official docs — a library (Next.js, MUI, better-auth, Drizzle, NestJS, …), an external API spec (ECPay, data.gov.tw, …) or a regulation (law.moj.gov.tw) — put a `// https://…` link to that page above the code, or at the top of the file when the whole file follows it, pointing at the installed version when the site versions its docs. Keep existing links (unless the user removed that link); when the code no longer follows the linked page, fix or delete the link in the same change. Links don't count toward the one-or-two-comments signal below.

Never write:

- a restatement of the next line, or of a field/constant name (`// 綠界折讓單號` on `allowanceNo`)
- the reasoning from our conversation, or a defence of your own tradeoff
- JSDoc on a private helper
- a description of what the code currently does — it becomes a lie after the next change

**Adding more than one or two comments to a change is itself the signal** that the code isn't saying enough. Fix the naming or the structure instead; do not narrate.

When a change makes an existing comment false, fix or delete it in the same change — a stale comment is worse than none. Don't hardcode identifiers into comments; they rot into misinformation after a rename.

## Implementation Approach

**Default: act, don't ask.** Ask only when the answer changes the data model, an API contract, or requires an irreversible or outward-facing action (shared-DB migration, deploy, push). For every other ambiguity, decide and proceed, then list the assumptions you made in the reply so the user can correct them afterward. This overrides "If uncertain, ask" in the vendored guidelines below.

Decide in this order:

1. **Official docs for the installed version** — check the version in `package.json` / `node_modules` first, never rely on memory. Next.js (`node_modules/next/dist/docs/`, next-devtools MCP), MUI (mui-mcp), better-auth, Drizzle, NestJS, next-intl, SWR, Zod, etc. Use the documented pattern over a workaround; never use APIs the docs mark deprecated.
2. **The existing pattern in this repo** — when the docs leave room, match how the codebase already does it.
3. **The most mainstream option** — when neither settles it.

## Behavioral Guidelines

Vendored from <https://github.com/multica-ai/andrej-karpathy-skills/blob/main/CLAUDE.md> (headings demoted one level). Don't add rules here — put project rules in the sections above, so this stays diffable against upstream.

Behavioral guidelines to reduce common LLM coding mistakes.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

### 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:

- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

### 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:

- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:

- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

### 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:

- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:

```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

---

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.
